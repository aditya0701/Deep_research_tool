How the Deep Research Agent Works

Four pages, each about one moving part: when the agent decides to search, what stops it from searching forever, what checks its final report before you see it, and one thing that isn't checked yet.

The short version: on every turn, the model itself decides whether to search again or answer now — that decision is genuinely its own, not scripted. What this project builds is everything around that decision: the tools it's allowed to use, the rules that shape its judgment, a hard cap so it can't search forever, and a check on its final claims before they reach you.

Use the left-hand list to jump between topics — this page doesn't need to be read top to bottom.

Search Query Calling

When does the agent decide to search, what rules is it following when it does, how does the call actually happen in code, and — the honest question — how sure can you really be that it's making the right call?

When does it call a search?

On every single turn, not just the first one. There's no separate "planning phase" — the same decision gets made fresh, turn after turn.

Model is handed the conversation so far + all 3 tools the same offer every turn: search again, or answer now — nothing forces either choice
It thinks first extended thinking runs before it responds — "what do I know, what's missing, is that missing piece worth a search?"
Decides: searchemits a tool call naming one tool + its input
Decides: answerwrites the final report as plain text, no tool call
"search" goes back to the top of this loop — up to the iteration cap

What rules is it following?

Four rules, shared by every version of this agent (direct questions and article research both use the same ones). Each governs a different part of the decision.

RULE 1 Decompose before judging An interpretive question ("what's the strategic significance of X") gets broken into fact sub-questions first. The judgment itself is never searched for — only written, at the end, from facts actually retrieved.
governs: WHAT it searches for
RULE 2 Verify before comparing Before comparing X to Y, confirm they're genuinely the same kind of thing — and if unsure what X or Y even is, search to check rather than guess from memory.
governs: WHETHER a comparison is even valid
RULE 3 Every claim must trace to a search If it wasn't retrieved during this conversation, it can't be stated as fact. This implicitly pushes it to search for anything it isn't already holding real evidence for.
governs: WHETHER to search at all before asserting
RULE 4 Budget awareness Prioritize the highest-value searches first, and stop once confident rather than exhausting every possible angle.
governs: WHEN to stop searching

How does the call actually happen, mechanically?

Three tools are described to the model up front — a name, a plain-language description, and the shape of the input it needs to provide:

web_search(query) — general search; description tells it to phrase queries as atomic facts, not compound questions
news_search(query) — recency-sensitive coverage
fetch_page(url) — read a full page when a snippet isn't enough

When the model decides to search, it doesn't run anything itself — it can't. It emits a request naming one of these three tools plus the input for it. The code reads that request, calls the real Python function, gets a real result back, and hands that result to the model on its next turn. The model never touches the network directly; it only ever asks, and only ever sees what comes back.

How can you actually be sure it's thinking the right thing?

Honestly — you can't be certain from the rules alone. A rule is a strong nudge, not a guarantee; that's the whole lesson this project inherited from a prior one where "don't hallucinate," worded carefully twice, still failed. What you can do is stop trusting it blindly and go check.

illustrative example, not a captured run

Every turn's reasoning is now recorded alongside every tool call it made, so a real run can be read back afterward like this:

iteration 0 · thinking — "This asks for strategic significance, which is a judgment, not a fact. I should first find out what was actually announced, and separately what the competing restriction actually says, before I try to connect them."
iteration 0 · tool — web_search("Z.ai open-source model release specifications")
iteration 1 · thinking — "I have the release details. I still don't have confirmation of the restriction itself — I shouldn't assume it's real or accurate just because the question states it that way."
iteration 1 · tool — news_search("US restrictions on Anthropic AI models")

That's what makes this checkable rather than a black box: read the trace, and see whether it actually decomposed the question the way rule 1 asks, or whether it reached straight for a compound search and hoped for the best.

The honest three-part answer: (1) you can now read its actual reasoning, iteration by iteration, instead of trusting the rules worked; (2) you can run the same known-tricky questions repeatedly (the eval suite exists for exactly this) and see whether good behavior holds up across runs, not just once; (3) even when the reasoning goes wrong, the budget cap and grounding check on the other two pages bound how much damage that can do — they don't fix bad thinking, but they stop it from running forever or reaching you completely unchecked.

Thinking vs. Fetching

The honest answer is that this isn't two things at all. There's no code anywhere that decides "think now" or "fetch now" — every turn is one call to the model, and thinking and fetching are just two parts of what comes back from it.

It reasons on every turn, whether it fetches or not

Tested directly, both ways, to be sure this claim is observed rather than assumed:

confirmed live Asked a trivial question with tool use explicitly forbidden ("what is 2+2, don't use tools"). The response still came back with a full reasoning_content field — "The user asked a simple math question and specifically told me not to use any tools, so I'll just answer directly." — even though it never touched a single tool. Reasoning isn't something that only happens when it's about to fetch; it happens every single turn, unconditionally.

One API response, two independent fields

This is the exact loop from agent.py — nothing simplified, nothing left out of what actually decides "fetch" vs. "stop":

# one call to the model - this is the ONLY place reasoning happens response = self.llm.call(system=self.system_prompt, messages=messages, tools=TOOLS) message = response.choices[0].message # the model's reasoning - present on EVERY turn, fetch or not reasoning = getattr(message, "reasoning_content", None) if reasoning: emit({"iteration": i, "thinking": reasoning}) # the fetch decision - just: did the SAME response also include tool_calls? if not message.tool_calls: return self._finish(question, message.content or "", ...) # stop, no fetch for tool_call in message.tool_calls: func = _TOOL_FUNCS.get(tool_call.function.name) result = func(**json.loads(tool_call.function.arguments)) # fetch, for real

Nothing here reads "if the model wants to think, do X; if it wants to fetch, do Y." There's exactly one branch: does message.tool_calls exist or not. Reasoning already happened either way, above that branch, unconditionally.

Two real turns, side by side

Both captured live from the actual client. Same response shape, same fields present — the only difference is whether tool_calls ended up empty or not, which is entirely the model's call, made during the same generation that produced the reasoning above it.

# turn where it decided to fetch (asked for Bitcoin's price) finish_reason: 'tool_calls' reasoning_content: "The user wants to know the current price of Bitcoin. Let me search for that." tool_calls: [Function(name='web_search', arguments='{"query": "current Bitcoin price today"}')] content: None # turn where it decided NOT to fetch (asked "what is 2+2", tools forbidden) finish_reason: 'stop' reasoning_content: "The user asked a simple math question and specifically told me not to use any tools, so I'll just answer directly." tool_calls: None content: "2+2 = 4."

Same two fields, every time. What decides "fetch or don't" is entirely inside the model's own generation — not something this codebase inspects or controls, only something it reads back afterward.

Which tool it fetches with — web_search / news_search vs. fetch_page

This part is steered by something we write: each tool's description is the only signal the model has for which one fits.

{ "name": "fetch_page", "description": ( "Fetch and read the full body text of a specific URL, e.g. one returned by " "web_search or news_search, when the snippet isn't enough detail." ), }

That description is written as a follow-up action, not a starting move — it explicitly points at URLs "returned by web_search or news_search." In practice this produces a two-hop pattern: a broad web_search/news_search call first to discover candidate URLs and snippets, then a fetch_page call on a specific one of those URLs if the snippet alone wasn't enough. Nothing in the code enforces this order — it's the tool descriptions doing the steering, the same lever rule 1-4 use for everything else.

On the fetch_page failures you noticed: flagged for later, not forgotten — some URLs returned by search don't scrape cleanly (paywalls, JS-rendered pages, timeouts), and fetch_page currently just returns an empty string or an error message in those cases rather than doing anything smarter about it. Worth its own pass once we're improving the loop.

Search Budget Enforcement

The model can search up to 8 times. On the 8th, its ability to search again is physically removed — not just discouraged.

1
search allowed
2
search allowed
3
search allowed
…
search allowed
8
search allowed
9
no tools given to the model — it cannot search even if it wants to

Turn 9 isn't the model choosing to stop. The code calls it one last time with an empty list of tools — there's nothing left for it to call. That's the whole trick: enforcement here means taking the capability away, not asking politely.

Grounding Check

Every report the model writes gets checked afterward, automatically, whether the model wants that or not.

Model writes its final reportplain text, may contain comparisons like "X vs Y"
Code splits it into sentenceslooking only for ones containing "vs" / "versus" / "compared to"
For each name in that sentence: does it appear anywhere in what was actually searched?"what was actually searched" = every real tool result collected during the loop
Found itsentence left alone
Not found"[UNVERIFIED: name not found in retrieved sources]" is appended, visibly

This runs on every return path out of the agent, unconditionally — the model has no way to skip it or mark itself as trustworthy enough to bypass it.

Identity Verification — the Gap

Right now, nothing checks whether the model actually looked something up before deciding what kind of thing it is.

What the final report claimsWas it ever actually searched?Status today
"Product A is a coding agent" Yes — web_search("what is Product A") appears in the trace would be fine
"Product B is also a coding agent, so it's comparable" No — no tool call anywhere in the trace ever mentions "Product B" should be flagged
Checking column 2 against the report and flagging row 2 automatically not built

The raw material for this already exists — every real tool call is logged during the loop. The missing piece is simply: after the model finishes, look at every entity it named, and check whether that entity's name shows up in any logged search. If it doesn't, that entity was never actually looked up — it was assumed. Same idea as the grounding check, just checking searches instead of results.

In one line: "code-enforced" in this project always means one of two things — take away the model's ability to do something, or check its output against real evidence after the fact and flag what doesn't hold up. A prompt instruction alone was tried and shown to fail in the prior project this one replaces; it's never trusted here to hold on its own.
